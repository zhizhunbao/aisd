## 🎬 序幕：我们在解决什么问题？

想象你雇了一个顾问，他读过互联网上几乎所有的书和文章，记忆力惊人，表达流利。但问题是：

1. **他的知识有截止日期** —— 2024 年之后发生的事他一概不知
2. **你公司的内部文档他没读过** —— 问他公司规章制度，他只能"编"一个
3. **他有时候会一本正经地胡说八道** —— 虽然听起来很有道理，但事实完全错误
4. **咨询费按字数收** —— 问得越多花得越多

这个"顾问"就是今天的 **大语言模型 (Large Language Model, LLM)**。

本节课要回答的核心问题是：**怎样让 LLM 从一个"博学但不靠谱"的顾问，变成一个"随时查资料、有据可查"的专业助手？**

答案就是 **RAG (Retrieval-Augmented Generation, 检索增强生成)**。

## 📚 第一章：认识 LLM —— 博学的"大脑"

### 1.1 一句话定义

**LLM = 用海量文本训练出来的超大型 Transformer 模型，能理解并生成类人文本。**

核心特征：
- 在 **数十亿到数万亿 token** 的文本上训练
- 基于 **Transformer 架构**（自注意力机制）
- 能执行广泛的 NLP 任务：文本补全、摘要、翻译、问答……

> 💡 **类比：** LLM 就像一个读了整个图书馆的学生——他记住了很多内容的"模式"和"规律"，但不是逐字记忆每本书。他回答问题时，是根据记忆中的模式"生成"答案，而不是翻书查找。

### 1.2 LLM 的四大核心组件

| 组件 | 含义 | 直觉理解 |
|------|------|---------|
| **Transformer 架构** | 自注意力 + 前馈网络的堆叠 | "大脑的神经回路" |
| **上下文长度 (Context Length)** | 一次能处理的最大 token 数 | "工作记忆的容量"——包括提示词 + 历史对话 + 生成的回答 |
| **参数 (Parameters)** | 模型中可学习的权重数量 | "记忆容量"——参数越多，能记住的模式越复杂 |
| **Token** | 模型处理文本的最小单位 | 不是"词"而是"子词片段"——如 `"unhappiness"` → `["un", "happi", "ness"]` |

### 1.3 主流 LLM 的"体检表"

| 模型 | 参数量 | 磁盘大小 (FP32) | 推理内存 (FP16) | 训练数据量 |
|------|--------|-----------------|-----------------|-----------|
| BERT (Large) | 340M | ~1.3 GB | ~1.5–2 GB | 3.3B 词 (~16 GB) |
| GPT-4o | ~200B | ~350 GB | ~400 GB | 570 GB (~300B tokens) |
| LLaMA 13B | 13B | ~26 GB | ~26 GB | ~1T tokens |
| LLaMA 70B | 70B | ~140 GB | ~140 GB | ~1T tokens |
| Mistral 7B | 7B | ~14 GB | ~14 GB | ~1T tokens |
| PaLM 540B | 540B | ~1 TB | ~1 TB | 780B tokens |

> 💡 **关键洞察：** 注意表格中的"推理内存"指的是 **GPU 显存 (VRAM)**，不是普通内存 (RAM)。GPT-4o 需要 ~400 GB 显存，只有数据中心才跑得动。即使是 Mistral 7B 的 14 GB FP16 也需要专业显卡（如 RTX 4090 的 24 GB VRAM）。**普通笔记本怎么办？** 答案是**量化 (Quantization)**——后面 Ollama 部分会看到，Mistral 7B 量化到 Q4 后只需 ~4 GB，可以用 CPU + 普通 RAM 运行，但速度会比 GPU 慢很多。

### 1.4 LLM 的四种类型

| 类型 | 代表 | 特点 |
|------|------|------|
| 通用语言模型 (General-purpose) | GPT 系列 | 什么都能干，但不一定精 |
| 指令微调模型 (Instruction-tuned) | AllenNLP | 按指令执行任务更准确 |
| 对话微调模型 (Dialogue-tuned) | DialoGPT | 更适合多轮对话 |
| 领域特定模型 (Domain-specific) | BioBERT | 在特定领域（如生物医学）表现优异 |

### 1.5 ChatGPT 是怎么训练出来的？

ChatGPT 的训练不是一步到位的，而是**三步走**：

1. **预训练 (Pre-training)** —— 在海量文本上学习语言规律（自监督学习）
2. **有监督微调 (Supervised Fine-Tuning, SFT)** —— 用人工标注的"问答对"教它按指令回答
3. **人类反馈强化学习 (RLHF)** —— 人类对多个回答排序，训练奖励模型，再用 PPO 优化

**现代升级：宪法 AI (Constitutional AI, CAI)**

Claude 和 GPT-4o 采用了更先进的方法——不再让人类逐条打分，而是给模型一套"宪法"（行为准则），让模型**自我评判和修正**。

> 💡 **类比：** RLHF 像是老师逐题批改作业；CAI 像是给学生一本"校规"，让他自己检查作业是否违规——效率更高，更可扩展。

### 1.6 ❗ LLM 的致命问题——五大局限性

LLM 很强大，但它有**无法忽视的结构性缺陷**：

| 局限性 | 问题本质 | 具体影响 |
|--------|---------|---------|
| **知识截止 (Knowledge Cutoff)** | 训练数据有截止日期 | GPT-5 的知识截止于某个日期，之后的事情它不知道 |
| **有限上下文 (Limited Context)** | 一次能处理的 token 数有上限 | 超长文档无法一次性理解 |
| **按 Token 收费 (Per-Token Pricing)** | 输入输出都按 token 计费 | 处理大量文档成本很高 |
| **幻觉 (Hallucination)** | 生成不存在的"事实" | 一本正经地胡说八道，用户难以辨别 |
| **缺乏专业知识 (Lack of Specialized Info)** | 没见过你的私有数据 | 无法回答公司内部问题 |
| **隐私安全 (Privacy & Security)** | 数据发送到外部 API | 敏感数据泄露风险 |

> 🔑 **故事转折点：** LLM 的知识是"刻在参数里"的——一旦训练完成，它就停止学习了。要更新知识，唯一的办法是重新训练，成本动辄数百万美元。我们需要一种方法，让 LLM **不重新训练就能获得新知识**！

## 🎭 第二章：RAG 登场——给 LLM 一本"参考书"

### 2.1 核心思想：从"闭卷考试"到"开卷考试"

**RAG (Retrieval-Augmented Generation, 检索增强生成)** 的核心思想很简单：

> **不要让 LLM 凭记忆回答，而是先帮它查到相关资料，再让它基于资料回答。**

这就是从"闭卷考试"变成"开卷考试"——学生（LLM）能力没变，但因为可以翻书（检索），回答质量大幅提升。

### 2.2 RAG 解决了什么问题？

| LLM 的问题 | RAG 的解决方式 |
|-----------|---------------|
| 知识截止 → 不知道最新信息 | 知识库可以**随时更新**数据 |
| 缺乏专业知识 → 不懂你的领域 | 知识库放入**领域特定文档** |
| 幻觉 → 编造答案 | 回答基于检索到的**真实文档**，可追溯 |
| 隐私风险 → 数据外泄 | 知识库部署在**本地**，数据不外传 |
| 高成本 → 重新训练太贵 | 只需更新知识库，**不需重新训练模型** |

### 2.3 RAG 的起源

RAG 这个概念来自 2020 年的论文：

> *"Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks"* (Lewis et al., 2020)

论文的核心观点：对于**知识密集型任务**（需要大量事实知识的任务），纯参数记忆不够用，需要用**外部检索**来增强。

> 🔑 **关键区别：** 微调 (Fine-tuning) 是"让 LLM 记住新知识"（改参数），RAG 是"让 LLM 查到新知识"（不改参数）。微调贵、慢、且可能忘记旧知识；RAG 便宜、快、且知识可随时增删。

## 📖 第三章：RAG 系统全解——从文档到回答的完整流程

### 3.1 前置步骤：构建知识库

在 RAG 能工作之前，必须先准备好"参考书"——即**向量化的知识库**：

```
📄 文档收集 (Collect)
    │
    ▼
✂️ 文档分块 (Chunking)
    │  ├── 固定大小分块 (Fixed Size) —— 简单但可能截断语义
    │  └── 自然边界分块 (Natural Boundaries) —— 按段落/标题分割，保留语义完整性
    │
    ▼
🔢 嵌入编码 (Embedding)
    │  将每个 chunk 转为高维向量 [0.48, 0.33, …, -0.51]
    │
    ▼
💾 存入向量数据库 (Vector Database)
       ├── ChromaDB    ├── Faiss
       ├── Weaviate    ├── Qdrant
       ├── Milvus      └── Elasticsearch
```

> 💡 **类比：** 知识库构建就像图书馆编目——你不能把整本书塞进一个目录卡片里（太长），而是按章节摘要（分块），然后给每个摘要一个索引号（嵌入向量），存进分类系统（向量数据库）里。

### 3.2 RAG 工作流程

当用户提问时，RAG 的三步流程：

**Step 1: 解析 (Parsing)** → 将用户的问题转为嵌入向量

**Step 2: 索引检索 (Indexing & Semantic Search)** → 在向量数据库中找到语义最相关的 chunks

**Step 3: 增强生成 (Augmented Generation)** → 将检索到的 chunks 塞进 prompt，让 LLM 基于这些上下文回答

```python
# RAG Prompt 模板（核心思想）
Prompt_Template = """answer the question based only the following context:
{context}
---
Answer the question based on the above context: {question}"""
```

> 💡 **关键词 "based only"：** 注意这个 prompt 模板明确要求 LLM **只能根据提供的上下文回答**。这就是 RAG 抑制幻觉的核心机制——如果检索到的文档里没有答案，LLM 应该说"我不知道"而不是编造一个。

### 3.3 分块方法 (Chunking Methods) 详解

分块是 RAG 质量的关键——分块太大，检索不精确；分块太小，丢失上下文。

| 分块策略 | 原理 | 优点 | 缺点 |
|---------|------|------|------|
| **固定大小 (Fixed Size)** | 每 N 个 token 切一刀 | 实现简单 | 可能截断句子/段落 |
| **自然边界 (Natural Boundaries)** | 按段落、标题、句子分割 | 保留语义完整 | 实现复杂，chunk 大小不均匀 |

> 💡 **实践建议：** 通常还会加 **overlap（重叠）**——相邻 chunk 之间重叠 50-200 tokens，确保跨 chunk 边界的信息不丢失。

### 3.4 向量数据库 (Vector Database)

向量数据库不同于传统关系型数据库——它存储的不是行列数据，而是**高维向量**，核心操作是**相似度搜索**而不是精确匹配。

> 🔑 **故事转折点：** RAG 系统搭建完成！但问题来了——你怎么知道你的检索结果好不好？检索到的 chunk 不相关怎么办？我们需要**量化评估检索质量**的方法！

## 🏆 第四章：检索质量评估——你的 RAG 检索得好不好？

### 4.1 核心痛点：为什么要评估检索？

想象你用 Google 搜索一个技术问题。如果第一页全是广告，或者你要翻到第三页才找到答案，你会觉得 Google 这个引擎"很烂"。

RAG 的检索部分，这就是给大模型的 **专属 Google 搜索引擎**：
- 如果检索给的资料是**错的**（不相关） → LLM 就会胡说八道。
- 如果检索给的资料**排在太后面** → LLM 可能因为上下文窗口限制根本看不到它。
> 🔑 **核心结论：** RAG 系统回答质量的**下限由大模型决定**（大模型越聪明，越能兜底），但**上限完全由检索质量决定。**因为只有把正确的参考资料喂给模型，它才能答对。我们不能靠主观感觉，必须用数学指标来量化"检索系统有多好"。

---

### 4.2 四大指标：用"搜网页"的日常例子来理解

假设我们要在海量知识库中搜索关于"什么是 RAG 算法"的内容：

#### ① RR@k (倒数排名，Reciprocal Rank) —— "我只想最快找到第一个正确答案"
- **日常场景**：你查一个单词的意思，你只在乎**第一条结果**对不对。
- **计算逻辑**：找到**第一个**相关文档排在第几位（Rank = r）。得分 = `1/r`。
- **例子**：
  - 如果拿到的第 1 个 chunk 就是你要的文档：RR = 1/1 = **1.0 满分**。
  - 如果前 2 个都在胡扯，第 3 个才是你要的文档：RR = 1/3 = **0.33 分**。
  - *(注：如果是评估多个问题的 RR 然后求平均，就是常常听到的 MRR, Mean Reciprocal Rank)*

#### ② Precision@k (精确率) —— "你给我的前 k 个结果里，有多少垃圾？"
- **日常场景**：你点开搜索前 5 个结果（k=5），发现 3 个有用，2 个是没用的广告。
- **关注点**：返回的信噪比。
- **公式**：`前 k 个结果中真正相关的数量 / k`。
- **例子**：前 5 个里中了 3 个，Precision@5 = 3/5 = **60%**。

#### ③ Recall@k (召回率) —— "知识库这座金山里的金块，捞上来了多少？"
- **日常场景**：假设知识库（上帝视角）里一共有 10 篇高质量的 RAG 教程，你的检索系统在前 5 个结果中，捞到了其中的 3 篇。
- **关注点**：有没有漏网之鱼？
- **公式**：`前 k 个结果中检索到的相关文档数 / 库里所有相关文档的总数`。
- **例子**：总共有 10 篇，找回了 3 篇，Recall@5 = 3/10 = **30%**。

> 💡 **RAG 中的黄金法则：** 在 RAG 系统中，**Recall（找全）通常比 Precision（找准）更关键**。
> 为什么？因为你只要把相关资料找出来扔进 prompt，强大的大模型（如 GPT-4）非常擅长忽略那些不相关的"垃圾文档"（低 Precision 没关系）；但如果最关键的那份文档没被检索出来（低 Recall），大模型也会巧妇难为无米之炊，只能胡编乱造。

---

#### ④ NDCG@k (归一化折损累积增益) —— "不仅内容要找得对，还得按好坏顺序完美排好！"
这是最复杂但也是**最专业、考频最高**的搜索排序指标。
- **日常场景**：不是所有相关文档的价值都一样。有些干货满满极其重要（打 3 分），有些只有一点用（打 1 分），毫无用处的（打 0 分）。最牛的搜索系统应该把 **3 分的置顶排第 1，1 分的放中间，0 分的垫底**。
- **三个字母拆解**：
  - **G (Gain, 增益)**：文档本身的相关性得分（`rel_i`）。
  - **D (Discounted, 折损惩罚)**：对"重要文档排在后面"的惩罚机制。分母是位置的对数 `log2(位置+1)`，排得越靠后，除以的惩罚系数越大。
    - *即：3分的绝世好文排第1，你得纯纯的3分；被蠢系统排到第5，你可能只能得1.5分。*
  - **N (Normalized, 归一化百分制)**：把上面带惩罚的得分加起来叫做 DCG。把 DCG 除以**理想情况下的最高分（IDCG）**，转换成 `[0, 1]`。

**📝 考试级手算推演（必背）：**
系统给出了 5 个 Chunk，你的打分序列是：`[1, 3, 2, 0, 1]`（注意，这里最厉害的 3 分排在了第 2 位）

**第一步：算当前得分 (DCG)** 
公式: $DCG = \frac{rel_1}{\log_2(2)} + \frac{rel_2}{\log_2(3)} + \frac{rel_3}{\log_2(4)} + ...$
- $DCG = \frac{1}{\log_2(2)} + \frac{3}{\log_2(3)} + \frac{2}{\log_2(4)} + \frac{0}{\log_2(5)} + \frac{1}{\log_2(6)}$
- $DCG ≈ 1 + 1.89 + 1 + 0 + 0.39 = \mathbf{4.28}$

**第二步：算完美情况的神之得分 (IDCG)**
把刚刚的分数完美排个降序：`[3, 2, 1, 1, 0]`
- $IDCG = \frac{3}{\log_2(2)} + \frac{2}{\log_2(3)} + \frac{1}{\log_2(4)} + \frac{1}{\log_2(5)} + \frac{0}{\log_2(6)}$
- $IDCG ≈ 3 + 1.26 + 0.5 + 0.43 + 0 = \mathbf{5.19}$

**第三步：归一化出分 (NDCG)**
- $NDCG = \frac{DCG}{IDCG} = \frac{4.28}{5.19} ≈ \mathbf{0.82}$
- **结论：** 你的检索系统得分为 82 分（达到了完美排序系统 82% 的功力）。

### 4.3 一图看懂指标差异

| 评价维度 | 灵魂拷问 | 代表指标 | 极致追求的目标 |
|--------|---------|---------|-------------|
| **首图体验** | "第一个对的结果在哪？" | **RR@k** | 第一条就是极其相关的结果 |
| **信噪比** | "你找来的资料里废话多不多？" | **Precision@k** | 每一条呈上的文档，都是切题的 |
| **大海捞针** | "库里的干货你是不是漏了？" | **Recall@k** | 只要库里有，哪怕你排末尾，也得给我捞出来 |
| **绝对排序** | "干货是不是按质量乖乖从上到下排好了？" | **NDCG@k** | 重中之重置顶，次等重要居中，废话垫底 |

## 📹 第五章：LLM 生成控制——Temperature 与 Top_p

解决了检索问题后，还需要控制 LLM 的**生成行为**：

| 参数 | 作用 | 低值效果 | 高值效果 |
|------|------|---------|---------|
| **Temperature** | 控制输出的随机性 | 确定性强、答案集中 | 多样性高、更有创意 |
| **Top_p** (Nucleus Sampling) | 限制候选 token 的概率范围 | 只选高概率的词 | 考虑更多候选词 |

> 💡 **RAG 场景建议：** 在 RAG 系统中，通常将 temperature 设**低**（如 0.1-0.3），因为我们需要 LLM 忠实于检索到的文档内容，而不是"发挥创意"。

## 📖 第六章：RAG 实战——LangChain 框架与开源部署

### 6.1 RAG 框架选型

有很多工具和框架可以构建 RAG 系统：

- **LangChain** —— 最流行的 RAG 框架，模块化架构
- **LlamaIndex** —— 专注于数据索引和检索
- **Haystack** —— 端到端的 NLP 框架
- **Semantic Kernel** —— 微软的 AI 集成框架

### 6.2 LangChain 核心能力

LangChain 之所以成为首选，因为它提供了：

1. **模块化架构** —— 灵活替换各组件（不同 LLM、不同向量数据库）
2. **链式调用 (Chaining)** —— 将多个服务串联成复杂工作流
3. **Agent 交互** —— 目标驱动的代理，可以自主决定使用哪些工具
4. **记忆与持久化 (Memory)** —— 跨会话保持对话状态
5. **开源社区** —— 活跃的社区和丰富的插件生态

## 📚 第七章：LLM 评估——怎么判断哪个模型最好？

### 7.1 社区驱动评估：Chatbot Arena

[Chatbot Arena](https://huggingface.co/spaces/lmarena-ai/chatbot-arena-leaderboard) 是一个**人类盲评**排行榜——用户同时和两个匿名模型对话，选择更好的回答，最终生成 ELO 评分排名。

### 7.2 系统化评估：HELM

**HELM (Holistic Evaluation of Language Models)** 是斯坦福推出的全面评估框架，从六个维度评估 LLM：

| 维度 | 含义 |
|------|------|
| **Accuracy** (准确性) | 回答是否正确 |
| **Calibration** (校准性) | 模型对自己答案的置信度是否准确 |
| **Robustness** (鲁棒性) | 面对对抗性输入是否稳定 |
| **Fairness** (公平性) | 对不同群体是否有偏见 |
| **Bias** (偏见) | 输出是否反映社会偏见 |
| **Efficiency** (效率) | 推理速度和资源消耗 |

> 💡 **核心观点：** 评估 LLM 不能只看"准确率"。一个 95% 准确但对少数群体有偏见的模型，在生产环境中可能比 90% 准确但公平的模型更危险。

### 技术转换总结

| 从 → 到 | 解决了什么核心问题？ |
|---------|---------------------|
| **纯 LLM → RAG** | 知识截止、幻觉、缺乏专业知识 → 实时检索外部文档回答 |
| **随意检索 → 评估指标** | 不知道检索好不好 → 用 NDCG/Recall/Precision 量化检索质量 |
| **高随机性 → 生成控制** | LLM 输出不稳定 → 用低 temperature 确保忠实于检索内容 |
| **手写管道 → LangChain** | 组件拼接复杂 → 模块化框架快速构建 |
| **闭源 API → 开源本地** | 成本高+隐私风险 → Ollama 本地部署 7B/14B 模型 |
| **主观感受 → HELM** | 不知道哪个模型好 → 六维度系统评估 |
