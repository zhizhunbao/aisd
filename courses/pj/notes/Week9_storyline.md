# Week 9 故事线：ML 系统的"基建工程"——从裸机到全自动平台

> **Source:** `CSI-CST8510-Week9.pptx`
> **核心主题：** 如何搭建一个支撑 ML 全生命周期的基础设施？从底层存储到顶层开发环境，四层架构像盖楼一样层层叠加。
> **故事线：** 盖一栋 ML 大楼——地基（存储计算） → 水电管道（资源调度） → 装修（ML 平台工具） → 入住（开发环境）

---

## 🎬 序幕：我们在解决什么问题？

想象你训练了一个很棒的 NLP 模型，在 Jupyter Notebook 里跑得很好。但接下来呢？

- 数据存在哪里？模型参数存在哪里？
- 怎么让 100 个用户同时调用它？
- 模型更新后怎么自动重新部署？
- GPU 资源怎么在多个团队之间分配？

> 💡 **一个 ML 模型从"实验成功"到"生产可用"，中间隔着的不是代码，而是一整栋基础设施大楼。**

这就是本周的核心问题：**ML 系统需要怎样的基础设施？**

答案是四层架构——从底层到顶层，每一层解决一类问题：

| 层次 | 解决什么问题 | 核心工具 |
|------|-------------|---------|
| ① 存储与计算 (Storage & Compute) | 数据放哪里？算力从哪来？ | HDD/SSD, Cloud, GPU |
| ② 资源管理 (Resource Management) | 多个任务怎么排队？谁先跑？ | Airflow, Slurm, K8s |
| ③ ML 平台 (ML Platform) | 模型/特征/部署怎么管理？ | SageMaker, MLFlow, Feast |
| ④ 开发环境 (Dev Environment) | 开发者在哪里写代码做实验？ | Jupyter, VS Code, Git |

## 📚 第一章：地基——存储与计算层 (Storage & Compute)

### 1.1 为什么先讲"地基"？

> 🔑 **没有数据存储和计算资源，一切 ML 工作流都无从谈起。**

就像盖楼必须先打地基——不管你的 ML 模型多先进，没有地方存数据、没有 GPU 跑训练，一切都是空谈。

### 1.2 存储层 (Storage)

存储层的任务很简单：**把数据安全地放好**。

- 最基础的存储介质：**HDD**（机械硬盘，便宜但慢）和 **SSD**（固态硬盘，快但贵）
- 现在存储已经**完全商品化**，大部分公司直接用 **云存储**（AWS S3, Azure Blob, GCP Cloud Storage）

### 1.3 计算层 (Compute)

计算层的任务：**提供算力跑 ML 工作负载**。

计算资源可以切分为更小的单元并发使用：

```
计算资源切分层次：
┌──────────────────────────────────┐
│  物理机器 (Physical Machine)      │
│  ├── 线程 (Threads)              │  ← 最细粒度，共享内存
│  ├── 容器 (Containers)           │  ← 隔离的运行环境
│  └── Pods                        │  ← K8s 调度单元，多容器组合
└──────────────────────────────────┘
```

### 1.4 关键指标：计算利用率 (Compute Utilization)

**Compute Utilization = 作业实际 FLOPS / 计算单元最大 FLOPS 能力**

> 💡 **记忆技巧**：就像一条高速公路，你的车能跑到 200km/h（最大 FLOPS），但实际因为红灯、上下坡等因素只跑了 100km/h（实际 FLOPS），利用率就是 50%。

实际中通常只能达到 **~50%** 的利用率——这意味着一半的算力在"空转"。

### 1.5 云成本的现实

- 云端支出约占上市软件公司收入成本的 **50%**（a16z 数据）
- 部分公司因此进行 **"云回迁" (Cloud Repatriation)**——将工作负载从公有云迁回自有数据中心

> 🔑 **故事转折点：** 地基打好了（有存储、有算力），但一个现实问题来了——这么多计算资源怎么分配？多个 ML 任务怎么排队？谁先跑？→ 我们需要**资源管理层**！

## 📖 第二章：水电管道——资源管理层 (Resource Management)

### 2.1 从 Cron 到调度器：依赖关系的挑战

最原始的任务调度工具是 **Cron**——在固定时间运行重复任务。

但 Cron 有一个致命缺陷：**无法处理任务之间的依赖关系**。

> 💡 **例子：** 你的 ML 工作流是：数据清洗 → 特征工程 → 模型训练 → 评估。如果用 Cron 设定每个任务在固定时间跑，万一"数据清洗"没做完，"特征工程"就已经开始了——这就出问题了！

**调度器 (Scheduler)** 就是升级版的 Cron——它理解 **DAG（有向无环图）**，知道哪些任务依赖哪些任务，按正确顺序执行。

### 2.2 调度器 vs 编排器：一个管"时间"，一个管"资源"

这是一个容易混淆但很重要的区分：

| 维度 | 调度器 (Scheduler) | 编排器 (Orchestrator) |
|------|:------------------:|:--------------------:|
| 关心什么 | **When** + **What** | **Where** |
| 核心问题 | 何时运行？需要什么资源？ | 从哪里获取资源？ |
| 抽象层级 | 高层：DAG、优先级队列、用户配额 | 底层：机器、实例、集群、副本 |
| 代表工具 | Slurm, Airflow | **Kubernetes** |
| 比喻 | 餐厅经理（安排顾客点菜顺序） | 厨房主管（调配厨师和灶台） |

### 2.3 Slurm 示例：声明式资源请求

```bash
#!/bin/bash
#SBATCH -J JobName           # 作业名称
#SBATCH --time=11:00:00      # 运行时间上限
#SBATCH --mem-per-cpu=4096   # 每 CPU 分配 4GB 内存
#SBATCH --cpus-per-task=4    # 每个任务 4 个 CPU 核
```

> 💡 **关键洞察：** Slurm 是 HPC（高性能计算）集群中最常用的调度器。你只需要"声明"需要什么资源，调度器自动排队和分配。这种**声明式 (declarative)** 风格也是 Kubernetes 的设计哲学。

### 2.4 Airflow：第一代工作流管理的教训

**Airflow** 由 Airbnb 开发，是最早的工作流管理工具之一。

**优点：**
- 庞大的算子库 (operators)
- 易于与多种云服务商集成

**三大致命缺陷：**

| 缺陷 | 含义 | 后果 |
|------|------|------|
| **单体架构 (Monolithic)** | 整个工作流打包在一个容器中 | 一个步骤失败，整个流程重启 |
| **不可参数化 (Not Parameterized)** | 无法向 DAG 传递参数 | 想试不同学习率？必须创建 N 个工作流！ |
| **静态 DAG (Static)** | 无法在运行时动态创建步骤 | 无法根据中间结果自动调整后续步骤 |

> 🔑 **故事转折点：** Airflow 的三个缺陷说明了第一代工具的局限性。新一代编排器 **Argo** 和 **Prefect** 解决了这些问题（支持参数化、动态 DAG、微服务架构）。→ 但资源调度只是"水电管道"，ML 系统还需要更高层的工具——**ML 平台**！

## 🎭 第三章：装修——开发环境 (Development Environment)

### 3.1 开发者的日常工作台

开发环境是 ML 工程师每天"住"的地方，包含三大组件：

| 组件 | 功能 | 代表工具 |
|------|------|---------|
| **IDE** | 写代码、调试 | Jupyter Notebook, VS Code, PyCharm |
| **版本控制** | 跟踪代码/数据/模型变化 | Git, DVC, Weights & Biases |
| **CI/CD** | 自动化测试和部署 | Jenkins, GitHub Actions |

### 3.2 Notebook：不仅仅是 IDE

Notebook 的独特优势——**有状态 (Stateful)**：

- 运行完成后保留状态 → 不用从头重跑
- 程序中断后可从断点恢复 → 大数据集实验的"存档点"
- 可以嵌入图像、LaTeX 文档、表格 → 代码 + 文档一体化

基于 Notebook 的工具生态：

| 工具 | 功能 | 一句话 |
|------|------|--------|
| **Papermill** | 参数化执行 | 同一个 Notebook 自动跑 N 组超参数 |
| **Commuter** | 共享平台 | 团队内找、看、分享 Notebook |
| **nbdev** | 文档+测试 | 代码、文档、测试写在同一个地方 |

> 💡 Netflix 在**生产环境**中使用 Notebook——不只是实验工具，也可以是生产工具。

### 3.3 容器 (Container) 与 Docker

当 ML 模型要在生产环境中服务时，面临一个核心问题：**环境一致性**。

> 💡 **经典场景：** "在我的电脑上能跑啊！" → Docker 容器就是解决这个问题的。

**Docker 容器 = 一个自包含的运行环境**：

- 包含代码、运行时、系统工具、库和设置
- 在任何安装了 Docker 的机器上一致运行
- 由 **Dockerfile**（配方）构建

Docker 五大优势：

| 优势 | 意义 |
|------|------|
| **Portability（可移植性）** | 一次构建，到处运行 |
| **Consistency（一致性）** | 开发、测试、生产行为相同 |
| **Isolation（隔离性）** | 互不干扰 |
| **Scalability（可扩展性）** | 一键扩缩容 |
| **Version Control（版本控制）** | Docker Hub 共享镜像 |

### 3.4 Pod：容器的"组队"

**Pod** 是 Kubernetes 中最小的部署单元 = 一组紧密协作的容器。

```
Pod 结构：
┌─────────────────────────────────┐
│  Pod                            │
│  ├── Container A (Model API)    │  共享 IP、端口空间
│  ├── Container B (Logging)      │  可通过 localhost 通信
│  └── Shared Storage             │  共享挂载存储
└─────────────────────────────────┘
```

> 🔑 **关键概念：** Pod 是 K8s 扩缩容的**原子单位**——你不是增减容器，而是增减 Pod。

## 🏆 第四章：精装——ML 平台 (ML Platform)

### 4.1 为什么需要 ML 平台？

有了存储、计算、调度、开发环境，模型可以训练和部署了。但新的问题来了：

- 部署了 50 个模型版本，怎么管理？
- 训练和推理使用的特征不一致怎么办？
- 模型回滚到旧版本，怎么快速恢复？

> 🔑 **ML 平台 = 模型全生命周期管理工具集**

三大核心组件：

```
┌──────────────────────────────────────────┐
│  ML Platform 三大组件                     │
│                                          │
│  ① Model Deployment（模型部署）          │
│     → 把模型推到生产环境，暴露 API        │
│                                          │
│  ② Model Store（模型存储）               │
│     → 管理模型的"身份证"（元数据）        │
│                                          │
│  ③ Feature Store（特征存储）             │
│     → 保证训练和推理特征一致              │
└──────────────────────────────────────────┘
```

### 4.2 选型的两个关键维度

| 维度 | 选项 A | 选项 B |
|------|--------|--------|
| **云兼容性** | 支持你的云服务商 ✅ | 仅支持特定云 ⚠️ |
| **开源 vs 托管** | 开源（自控，需工程资源） | 托管服务（省心但贵，可能有隐私合规问题） |

### 4.3 模型部署 (Model Deployment)

**最成熟的 ML 平台组件**——将模型推送到生产环境并暴露为 API **端点 (endpoints)**。

| 提供商 | 工具 |
|--------|------|
| AWS | SageMaker |
| Azure | AzureML |
| GCP | VertexAI |
| 初创公司 | MLFlow Models, Seldon, Cortex, Ray-Serve |

### 4.4 模型存储 (Model Store)

仅存储模型权重文件 (`model.pt`) 远远不够。一个完整的模型存储需要记录 **8 类元数据**：

| 元数据类型 | 内容 | 为什么需要？ |
|-----------|------|-------------|
| Model Definition | 损失函数、层数、每层参数数 | 重现实验 |
| Model Parameters | 训练后的实际参数值 | 加载推理 |
| Featurize & Predict | 特征化和预测函数 | 保证推理一致 |
| Dependencies | Python 包版本 | 环境重现 |
| Data | 数据存储指针 | 溯源 |
| Model Generation Code | GitHub 仓库指针 | 代码审计 |
| Experiment Artifacts | 损失曲线、性能指标 | 对比模型 |
| Tags | 标签 | 检索 |

> 💡 **记忆口诀：** "定参函依数码品标"（定义、参数、函数、依赖、数据、代码、制品、标签）

### 4.5 特征存储 (Feature Store)

解决三个核心问题：

| 问题 | 含义 |
|------|------|
| **Feature Management** | 特征太多怎么组织管理？ |
| **Feature Computation** | 特征计算逻辑怎么复用？ |
| **Feature Consistency** | 训练和推理用的特征怎么保证一致？ |

两大工具对比：

| 工具 | 优势 | 劣势 |
|------|------|------|
| **Feast** | 擅长批量特征 (batch) | 流式特征 (streaming) 弱 |
| **Tecton** | 同时支持在线和批量特征 | 需要深度集成 |

```
│  ✅ 解决：数据存储 + 算力提供                                │

└──────────────────────────────────────────────────────────────┘
```

### 关键概念对比总结

| 从 → 到 | 解决了什么核心问题？ |
|---------|---------------------|
| 裸机 → 云存储 | 存储商品化，无需自建机房 |
| Cron → Scheduler | 加入依赖关系，DAG 调度 |
| Scheduler → Orchestrator | 从"管时间"到"管资源" |
| Airflow → Argo/Prefect | 解决单体、静态、不可参数化三大缺陷 |
| 手动部署 → ML Platform | 模型/特征/部署的全生命周期管理 |
| 本地开发 → Docker/Pod | 环境一致性 + 可扩展性 |
