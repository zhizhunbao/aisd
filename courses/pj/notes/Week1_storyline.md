# Week 1 故事线：如何判断 GenAI 输出"好不好"？——评估基础全链路

> **Source:** `Module1.1-Foundations-of-GenAI-Evaluation.ipynb`
> **核心主题：** LLM 的输出是非确定性的，传统的"对/错"测试不够用——我们需要一整套评估方法论来判断 GenAI 应用的好坏。
> **故事线：** 从"为什么要评估" → "评估有什么难" → "怎么评（三大范式）" → "用指标量化（有参考/无参考）" → "让 LLM 自己当裁判" → "裁判也有偏见怎么办"

---

## 🎬 序幕：我们在解决什么问题？

你的团队刚用 GPT-4 搭了一个客服 AI，老板问："这东西靠不靠谱？"

- 传统软件可以跑单元测试——输入 2+2，输出必须是 4。✅ **确定性验证 (Verification)**
- 但 GenAI 不一样——同一个问题"请解释量子力学"，每次回答都不同。❌ **非确定性验证**

> 💡 **核心直觉：** 传统软件评估是 **Verification**（验证——答案对不对）；GenAI 评估是 **Validation**（确认——整体效果好不好）。前者有标准答案，后者需要多维度综合判断。

那 GenAI 评估到底难在哪？为什么不能直接沿用传统测试方法？

---

## 📚 第一章：为什么评估对 GenAI 至关重要？

### 1.1 不评估会出什么问题？

| 风险 | 说明 | 例子 |
|------|------|------|
| **输出质量不可控** | 模型可能生成错误、有害的内容 | 医疗 AI 给出错误的用药建议 |
| **偏见与公平性** | 模型继承训练数据中的偏见 | 简历筛选 AI 歧视特定群体 |
| **模型漂移 (Model Drift)** | 性能随时间退化 | 客服 AI 在数据分布变化后回答越来越差 |
| **监管合规** | 不满足法律和伦理标准 | 违反 GDPR 隐私保护规定 |
| **有害输出** | 生成有毒、不安全的内容 | 内容生成 AI 产生仇恨言论 |

### 1.2 评估的十大价值

1. ✅ 确保输出质量 (Output Quality)
2. ✅ 检测偏见和公平性 (Bias & Fairness)
3. ✅ 监控模型漂移 (Model Drift)
4. ✅ 支持监管合规 (Regulatory Compliance)
5. ✅ 指导模型改进 (Model Improvement)
6. ✅ 建立用户信任 (User Trust)
7. ✅ 防止有害输出 (Harmful Outputs)
8. ✅ 衡量真实影响 (Real-world Impact)
9. ✅ 支持基准对比 (Benchmarking)
10. ✅ 指导部署决策 (Deployment Decisions)

> 🔑 **故事转折点：** 评估很重要，这已经清楚了。但 GenAI 评估**比传统评估难得多**——非确定性输出、缺少标准答案、主观性强。→ 我们需要理解**评估的挑战**！

---

## 🎭 第二章：GenAI 评估的核心挑战——为什么传统方法不够用？

### 2.1 Silent Failure——沉默式失败

GenAI 最可怕的不是"崩溃"，而是**看起来正常但实际上错了**。传统软件出错会抛异常、日志报警；LLM 出错时可能"自信满满地胡说八道"——这就是 **Hallucination (幻觉)**。

> 💡 **类比：** 传统软件 bug = 发高烧（明显症状）；GenAI bug = 无症状感染（看不出来但在传播错误信息）。

### 2.2 七大挑战

| 挑战 | 英文 | 说明 | 例子 |
|------|------|------|------|
| **全组件评估** | All Components Evaluation | 不能只评估 LLM，管道中任一组件（检索器、解析器等）都可能是瓶颈 | RAG 系统中检索器返回无关文档 → LLM 再强也回答不对 |
| **非确定性输出** | Non-deterministic Outputs | 同一输入 → 不同输出 | 同一问题问两次，答案可能完全不同 |
| **质量主观性** | Subjectivity of Quality | 评估标准因人而异 | AI 写的故事，有人觉得精彩，有人觉得平庸 |
| **缺少标准答案** | Lack of Ground Truth | 很多任务没有唯一正确答案 | 文本摘要——100 种写法都可以是对的 |
| **偏见检测困难** | Bias Detection | 微妙偏见难以自动发现 | 招聘 AI 隐性偏向某些人口统计特征 |
| **人工评估不可扩展** | Scalability of Human Eval | 大规模人工审核成本极高 | 审查上万张 AI 生成图片 |
| **对抗性鲁棒性** | Adversarial Robustness | 模型对恶意输入的抗干扰能力 | Prompt Injection 攻击 |

> 🔑 **故事转折点：** 知道了挑战，那到底应该用什么方法来评估？→ 六大评估范式 (Evaluation Paradigms) 登场！

---

## 📖 第三章：六大评估范式——工具箱里有哪些武器？

### 3.1 评估范式全景

| # | 范式 | 英文 | 做法 | 优势 | 局限 |
|---|------|------|------|------|------|
| 1 | **人工评估** | Human-in-the-Loop | 人类专家打分 | 金标准 (Gold Standard)，捕捉细微差异 | 成本高、不可扩展 |
| 2 | **自动指标** | Automated Metrics | 用预定义指标（BLEU、ROUGE）或 LLM-as-Judge | 快速、可扩展 | 可能遗漏主观质量 |
| 3 | **对抗测试** | Adversarial Testing | 用刁钻输入探测弱点 | 暴露脆弱性 | 需要专业设计 |
| 4 | **用户反馈** | User Feedback | 收集真实用户评价 | 反映实际体验 | 数据带噪声 |
| 5 | **A/B 测试** | A/B Testing | 将不同版本部署给不同用户群 | 衡量真实影响 | 需大流量 |
| 6 | **基准测试** | Benchmarking | 在标准化数据集上对比 | 客观、可复现 | 基准可能不代表实际场景 |

### 3.2 评估贯穿 SDLC 全生命周期

评估不是一次性的事——它跟随 GenAI 应用的每个阶段：

```
需求分析 → 数据准备 → 模型开发 → 验证测试 → 部署上线 → 运维监控
   ↓          ↓          ↓          ↓          ↓          ↓
定义评估    评估数据    迭代评估    全面评估    A/B测试    持续监控
标准/KPI    质量/偏差   自动指标    未见数据    用户反馈    漂移检测
```

> 🔑 **故事转折点：** 知道了"用什么方法"评估。但具体怎么给 GenAI 输出打分？有两条路——**有参考答案 vs 没有参考答案**。→ 评估类型 (Evaluation Types) 登场！

---

## 🏆 第四章：评估的两条路——有参考 vs 无参考

### 4.1 有参考评估 (Reference-Based Evaluation)

> **一句话定义：** 把 AI 的输出和"标准答案"做比较，看有多像。

**适用场景：** 有高质量参考数据时（如机器翻译、文本摘要）

**核心指标：**

| 指标 | 英文全称 | 衡量什么？ | 核心思路 |
|------|----------|----------|---------|
| **ROUGE** | Recall-Oriented Understudy for Gisting Evaluation | 摘要质量 | 计算生成文本与参考文本的 n-gram 重叠（偏 Recall） |
| **BLEU** | Bilingual Evaluation Understudy | 翻译质量 | 计算 n-gram 精确度（偏 Precision） |
| **METEOR** | Metric for Evaluation of Translation with Explicit ORdering | 翻译质量 | 考虑同义词和词干，比 BLEU 更细腻 |
| **BERTScore** | BERT-based Score | 语义相似度 | 用 BERT 嵌入做语义匹配，而非表面词汇匹配 |

**ROUGE-N 计算公式：**

```
ROUGE-N Recall    = 重叠的 n-gram 数 / 参考文本的 n-gram 总数
ROUGE-N Precision = 重叠的 n-gram 数 / 生成文本的 n-gram 总数
ROUGE-N F1        = 2 × Recall × Precision / (Recall + Precision)
```

**ROUGE 代码实现要点：**

```python
def rouge_n(reference, generated, n=1):
    # 1. 分词 → tokens
    # 2. 构造 n-gram → Counter
    # 3. 计算交集 → overlap
    # 4. recall = overlap / ref_count
    # 5. precision = overlap / gen_count
    # 6. f1 = 2 * R * P / (R + P)
```

> ⚠️ **局限：** 有参考评估可能**惩罚创造性但正确的输出**——如果 AI 的答案有效但与参考答案措辞不同，得分会很低。

### 4.2 无参考评估 (Reference-Free Evaluation)

> **一句话定义：** 不看"标准答案"，直接按评估标准打分。

**适用场景：** 开放式任务（对话、创意写作），或缺少标注数据的专业领域。

**评估维度（多维评估）：**

| 维度 | 英文 | 衡量什么？ |
|------|------|----------|
| **事实准确性** | Factual Accuracy | 信息是否正确？ |
| **相关性** | Relevance | 是否回答了问题？ |
| **流畅性** | Fluency/Grammar | 语言是否通顺？ |
| **连贯性** | Coherence | 逻辑是否通顺？ |
| **安全性** | Safety/Toxicity | 是否有害或有毒？ |

> 💡 **关键洞察：** GenAI 输出太复杂，单一指标无法全面评估。必须**多维度综合评判**——好比评价一篇作文，不能只看字数，还要看内容、逻辑、文采、格式。

> 🔑 **故事转折点：** 有参考评估靠计算重叠，无参考靠人类判断。但人工评估**太贵、不可扩展、有偏见**。有没有办法自动化？→ **LLM-as-a-Judge** 登场！

## ⚡ 第五章：用 AI 评估 AI——LLM-as-a-Judge 方法论

### 5.1 什么是 LLM-as-a-Judge？

> **一句话定义：** 用一个强大的 LLM（如 GPT-4）来自动评估另一个 AI 的输出质量。

**为什么不完全依赖人工？**

| 人工评估的问题 | 说明 |
|--------------|------|
| **主观偏差** | 更自信、更复杂的输出容易被误认为更准确 |
| **个人偏好** | 每个评估者有不同的标准和偏好 |
| **不可扩展** | 企业级评估需要审核数千个样本，成本极高 |

**LLM-as-a-Judge 的四大优势：**

| 优势 | 英文 | 说明 |
|------|------|------|
| **可扩展** | Scalability | 可同时评估数千个样本 |
| **低成本** | Cost-Effectiveness | 远低于人工评估成本 |
| **灵活** | Flexibility | 可针对特定领域微调或调整 Prompt |
| **复杂场景** | Complex Scenarios | 能评估多格式、多维度的复杂文本 |

### 5.2 三种 LLM-as-a-Judge 类型

| # | 类型 | 英文 | 输入 | 输出 | 最佳场景 |
|---|------|------|------|------|---------|
| 1 | **无参考单输出评分** | Single Output Scoring (w/o Reference) | 输出 + 评分标准 | 离散分数 | 简单独立评估（如客服回复）|
| 2 | **有参考单输出评分** | Single Output Scoring (w/ Reference) | 输出 + 参考 + 评分标准 | 离散分数 | 有标准答案的精确评估 |
| 3 | **配对比较** | Pairwise Comparison | 两个输出 + 评选标准 | 哪个更好 | 相对质量判断（A vs B）|

**示例：无参考评分**

```
输出待评估: "我理解您对配送延误的不满。我们的团队正在处理您的订单，
            您将在24小时内收到追踪号。"

评分标准 (Rubric 1-3):
  1 = 不专业或敷衍
  2 = 专业但解决方案不完整
  3 = 专业、有同理心、提供清晰解决方案

→ LLM 评分: 3（专业、有同理心、提供了明确的时间承诺）
```

**示例：有参考评分**

```
输出: "新环保法要求公司在2030年前减少30%的碳排放。"
参考: "2024年环保法要求500人以上公司在2030年前减少30%碳排放，
       并每年提交进度报告。"

→ LLM 评分: 3（准确但不完整——遗漏了公司规模要求和报告义务）
```

**示例：配对比较**

```
描述A: "我们的无线耳机提供20小时续航和降噪功能。"
描述B: "体验不间断的音乐——20小时续航、先进降噪、记忆海绵耳垫。"

→ LLM 判断: B 更优（更具体、更有吸引力、更多细节）
```

### 5.3 何时使用 / 何时避免

| ✅ 适合使用 | ❌ 应避免 |
|------------|----------|
| 主观质量评估（情感、摘要质量） | 有标准答案且客观指标就够了 |
| 需要理解复杂上下文和细微差别 | 需要二元判断（是/否） |
| 需要同时评估多个维度 | 极高风险决策（医疗、法律） |
| 传统指标（BLEU/ROUGE）遗漏质量方面 | — |
| 需快速评估大量样本 | — |

> 🔑 **故事转折点：** LLM-as-a-Judge 很强大，但它**自己也有偏见**！裁判不公正怎么办？→ 我们需要了解**五大偏见**及其缓解策略！

## ⚠️ 第六章：裁判的偏见——LLM-as-a-Judge 的五大陷阱

### 6.1 五大偏见

| # | 偏见 | 英文 | 表现 | 例子 |
|---|------|------|------|------|
| 1 | **裙带偏见** | Nepotism Bias | 偏向同家族 LLM 生成的文本 | GPT-4 评分时偏爱 GPT-3.5 的输出 |
| 2 | **权威偏见** | Authority Bias | 对来自权威来源的内容给更高分 | 标注为"哈佛研究"的文本得分更高 |
| 3 | **颜值偏见** | Beauty Bias | 偏爱格式美观的文本，忽略准确性 | 排版漂亮但内容有误的回答得高分 |
| 4 | **冗长偏见** | Verbosity Bias | 偏爱更长的回答 | 啰嗦但无新信息的回答 > 精准简洁的回答 |
| 5 | **位置偏见** | Positional/Attention Bias | 忽略中间内容，只关注开头和结尾 | 重要细节在中段被忽视 |

### 6.2 五大缓解策略

| 策略 | 对抗哪种偏见 | 做法 |
|------|------------|------|
| **Chain-of-Thought 推理** | 全部 | 让 Judge LLM 先推理再打分，减少草率判断 |
| **自一致性 (Self-Consistency)** | 全部 | 对同一输出生成多次评分→取平均/多数投票 |
| **多模型评估** | 裙带偏见 | 用多个不同厂商的 LLM 交叉评估 |
| **标准化输入长度** | 冗长偏见 | 要求所有输出控制在相同篇幅 |
| **匿名化来源** | 权威偏见 | 隐去输出的来源标识 |

> 💡 **核心记忆：** 偏见口诀 = **"裙权颜冗位"**（裙带、权威、颜值、冗长、位置）。

## 📋 最佳实践速查（考试必记）

| # | 最佳实践 | 原因 |
|---|---------|------|
| 1 | **评估所有组件**，不只评估 LLM | 管道中任一环节都可能是瓶颈 |
| 2 | **多维度评估**（准确性+相关性+流畅性+安全性） | 单一指标无法全面反映质量 |
| 3 | 有参考评估用 **ROUGE + BERTScore 组合** | ROUGE 看表面重叠，BERTScore 看语义 |
| 4 | 无参考评估用 **LLM-as-a-Judge + CoT** | 自动化 + 减少偏见 |
| 5 | 用 **多个不同 LLM 交叉评估** | 避免裙带偏见 |
| 6 | **标准化输入长度** | 对抗冗长偏见 |
| 7 | 评估贯穿 **SDLC 全生命周期** | 不是上线后才评估 |
| 8 | **持续监控模型漂移** | 数据分布变化会导致性能退化 |
