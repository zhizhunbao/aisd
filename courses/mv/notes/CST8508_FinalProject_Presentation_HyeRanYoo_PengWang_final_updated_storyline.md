# Lecture 11 故事线：基于 WebCam 的虚拟云台跟飞追踪系统

> **Source:** `CST8508_FinalProject_Presentation_HyeRanYoo_PengWang_final_updated.pptx`
> **核心主题：** 如何靠一个静止的笔记本摄像头，实现锁定并自动放大跟踪画面中央最明显的人？
> **故事线：** 从大海捞针（检测），到死缠烂打（跟踪），再到只取一瓢（找最大框），最后实现"智能导播"（截图居中显示）的进阶之路。

---

## 🎬 序幕：我们在解决什么问题？

想象一下你正在用笔记本电脑开视频会议，但你需要在房间里走动讲解。传统的定焦摄像头只能拍摄固定画面，一旦你走出核心区域就会显得很小，甚至出框。
我们需要一个**能够在摄像画面中实时自动追踪、并始终将你保持在画面中央**的“虚拟摄影师”。

**项目的最终目标是将 640x480 的原始静态全局画面，动态裁切放大为一个 480x480 并始终锁定主角的“特写镜头”**。

---

## 📚 第一章：基础设施与底层环境搭建

要完成这样一套端到端的机器视觉（CV）流水线，最大的难点往往在一开始：**将各种彼此独立的底层框架无缝拼接**。

在这个项目中，我们必须严格遵守一套版本匹配矩阵，任何一个模块的小差错都会导致整个项目跑不起来。
- **环境基石**：Python 3.11（这是红线，Python 3.13 会直接因为与 MMCV 的 C++ 拓展不兼容而导致失败）
- **检测利器**：PyTorch 2.2.2 + OpenMMLab 系列（MMCV 2.2.0, mmdetection 3.2.0）
- **追踪利器**：supervision 库的 ByteTrack

此外，我们还设计了一个解耦的思想：**将容易需要变动的阈值参数剥离在外的 `config.json`**，这样在后续实时调试时，就不必重启冗长的主循环。

> 🔑 **故事转折点：** 当环境搭建完毕能打通摄像头时，我们首先要面对的核心技术挑战：如何在拥挤或者复杂的房间背景下认出“人”来？ → **检测器开始登场！**

---

## 🎭 第二章：方案一——仅靠检测器 RTMDet-s（⚡ 找得到，但不连续）

为了在一帧画面里认出所有的“人”，我们启用了 OpenMMLab 的预训练利器：**RTMDet-s**。

**① 一句话定义：** RTMDet-s 是一个小型轻量化的实时目标检测模型。
**② 原理：** 输入图片，它利用内部神经元找特征，最终输出所有疑似目标的类别（label=0 代表人）、框（bbox）和概率分数（score）。
**③ 特点：** 它能在 COCO 数据集上达到 44.6% AP，最重要的是：**只有它能在不用 GPU 加速的纯粹 CPU 环境下跑到十几帧（满足实时要求）。**

### 2.1 ❗ 纯粹依赖单帧检测的致命问题

假设画面中有三个人在走动，单独跑检测器会出现：
1. **闪烁问题**：如果有人侧身了导致这一帧置信度降到 0.45（低于设定阈值 0.5），这个框就会在这一帧消失，下一帧又冒出来。
2. **缺乏身份（ID）观念**：模型只知道“这是一个人”，但不知道“这和上一秒的是同一个人”，于是无法针对某个人进行持续追踪任务。

> 🔑 **故事转折点：** 只有孤立的瞬时检测帧是无法做到“紧盯某人”的，我们需要一个记忆管理系统 → **目标追踪器 ByteTrack 登场！**

---

## 📖 第三章：方案二——引入 ByteTrack 多目标跟踪（⚡ 认得出大家，但跟谁呢？）

为了给上一帧和这一帧的人“连线”，我们启用了 **ByteTrack**。

**① 一句话定义：** 一种基于两阶框关联逻辑的追踪算法，能赋予每个框稳定的 UUID。
**② 原理：** 
- **高分优先（Stage 1）**：先把高确定性（Conf > 0.5）的人跟已有的轨迹通过 交并比（IoU，即位置重合度）匹配上。
- **低分挽救（Stage 2）**：对于因为短暂遮挡等原因分数变低的漏网之鱼，再次利用 IoU 尝试捞回，避免因为一帧没认清就切断跟踪线（通过设定 `lost_track_buffer = 30` 帧缓冲）。

### 3.1 ❗ 目标到底锁定谁的致命问题

有了 ByteTrack，我们现在能在每个人头上顶着稳定不变的 "ID:1"、"ID:2" 了，这很好。但画面里如果有三个人，我们的目标是要剪切一个特写镜头，**到底裁切哪一个人？**

> 🔑 **故事转折点：** 既然是单人汇报或跟踪场景，一般来说“离镜头最近的、占据屏幕面积最大的”通常是主角所在之处。 → **最大边界框逻辑（Largest BBox Filter）登场！**

---

## 🏆 第四章：方案三——锁定靶心与云台居中（✅ 智能跟飞完成）

我们在整个跟踪列表里，直接执行一次面积循环比对：计算每个框的长×宽，用 `np.argmax(areas)` **永远只高亮标红面积最大的那一个框**，将其选拔为所谓的“主角（TARGET）”。

接着，为了实现摄像机的智能云台跟飞（即使是虚拟实现的），我们分出了两步走：

### 4.1 像素偏移计算仪（Center Calculation）

计算原始全景画面的绝对中心点，再计算刚刚那个“红色最大靶心框”的中心点。
- `dx = 人中心x - 画面中心x`
- `dy = 人中心y - 画面中心y`
根据 dx 和 dy 的正负极判定主角偏移方向（上、下、左、右）。
考虑到物理防抖，为了防止主人公稍微晃一下头就让控制中心疯狂输出移动指令，必须设定**包含中心 5% 范围的防抖死区（Tolerance zone）**。

### 4.2 虚拟云台跟进视图（Crop & Center View）

既然没有物理伺服电机去转动相机，那我们就在软件端实现“裁剪追踪”——在原始全局画面中，围绕这红色的TARGET框，向外以 80% （`crop_padding_ratio = 0.8`）的比例圈出一片局部区域，切下来后再通过 `cv2.resize` 拉伸填充到一个 480x480 的固定画布上。并单独通过 `cv2.imshow` 弹出一个名为 `Person Focus` 的新窗口。

至此，无论主角走到全图的哪个偏僻角落，在裁切新窗口里，主角永远都如影随形、居于画面的绝对中心！

### 演进逻辑与局限对峙

| 实施阶段 | 解决了什么核心问题？ | 存在的极限边界分析（Limitation） |
| ------- | -------------------- | -------------------------------|
| **底层环境搭建** | PyTorch/MMCV底层的C++扩展跑通 | 无法支持 Python 3.13 较新的指令集，易碎的版本系统 |
| **检测：RTMDet** | 在全画幅里解决“找人”这一难题突破 | 完全依赖 CPU 推理，没有CUDA加速的情况下只能支持勉强的 10-15 帧。 |
| **追踪：ByteTrack** | 闪烁跳帧下的断路丢失痛点突破 | 没有特征匹配（ReID），人走出画面再进入的话会被当做一个全新的 ID，重新计算轨迹。 |
| **筛选：选取最大** | 多人混杂情况下的核心目标锁定突破 | 纯 2D 镜头无深度预测，极易被前排走动的无辜群众抢走所谓的“焦点屏幕最大框”。 |

- [ ] **理解环境版本的捆绑**：明白为何必须卡准 PyTorch 2.2.2 + MMCV 2.2.0 + Python 3.11 的版本死角。
- [ ] **性能与开销折中妥协**：明白选用 RTMDet-s 轻量化版本取代其它笨重框架的核心原因（无独立显卡依然可用的实时性保障）。
- [ ] **多重跟踪的兜底逻辑**：讲清楚 ByteTrack 是怎样试图从偶尔闪断的连续帧中还原事实的（高分先分配，低分再找寻）。
- [ ] **2D伪装的纵梁局限**：剖析“依靠二维像素面积变化”去推断“真实3D世界前中后距离景深”所蕴含的失效风险。
- [ ] **软去抖与硬件分离**：拆解 Center Tolerance 的原理，并厘清“软件层提取裁剪框追溯（算法）”与“云台伺服驱动相机（硬件）”之间的界限。
